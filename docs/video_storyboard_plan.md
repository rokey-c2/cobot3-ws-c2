## 0. 문제 정의 (프로젝트 전체 서사의 근거)

- 물류센터 자동화(AMR+로봇팔+컨베이어+소터)로 표준 작업 처리량은 높일 수 있지만, **예외
  상황·우선순위 변경 판단은 결국 사람이 해야 하는 영역**이라 완전 무인화로 없앨 수 있는
  부분이 아님.
- **기존 방식 (Before)**: 웹 기반 관제가 없으면, 사무실에 있는 담당자가 우선순위를 바꾸려면
  물류센터 현장에 **전화로 요청**해야 하고, 현장 작업자가 그 요청을 받아 대신 조작해야 함 —
  이 사이에서 지연/의사소통 오류가 생김.
- **우리 시스템 (After)**: Control Tower를 쓰면 사무실 담당자가 **웹으로 직접** 원격에서
  AMR·컨베이어를 조작할 수 있어서, "전화로 요청 → 현장에서 대신 조작"하는 중간 과정 자체가
  사라짐. 관제 담당자가 현장에 상주할 필요도, 현장에 연락할 필요도 없어짐.
- 영상 5번 비트(관제, 9장)가 정확히 이 Before→After를 보여주는 장면: 사무실에서, 전화 없이,
  웹으로 바로 우선순위를 바꾸고 그 결과가 물류센터에 실시간 반영되는 것.
- 이 문제 정의는 평가 배점표(6장) 1번 항목 "문제 정의: 해결하려는 현실 문제가 명확히
  서술되어 있다" (20점 항목의 세부 기준)에 대응.

## 1. 영상 기본 조건

- 길이: 목표 60초, 단 5번(관제) 비트가 서사 확정 후 분량이 늘어나 **65~70초로 소폭 연장
  가능성 있음** (9장 참고).
- 처음 제안된 캡처 포인트는 10개였으나, 60초에 10개는 컷당 평균 6초로 과함 →
  **핵심 비트로 압축**하기로 결정. 이후 논의를 거쳐 오프닝 맥락 샷을 추가해 **5비트**로 확정
  (아래 2장).

  "박스마다 정해진 목적지로 정확히 분류된다" 정도로 표현.

## 4. 배치 순서 결정 — 관제 시스템을 맨 뒤에

- 웹 관제(Control Tower)가 이 영상의 핵심 포인트.
- **뒤쪽 배치로 결정**: 물리 프로세스(1~3번)로 "현장"을 먼저 인지시킨 뒤, 마지막에
  "이걸 실시간으로 관제한다"는 반전/하이라이트로 마무리하는 게 60초 안에서 임팩트가 크고
  기억에도 남음.
- 트레이드오프로 논의된 대안(앞쪽 배치): 초반에 "이건 관제 시스템 영상"이라고 못박아서
  이후 물리 장면들을 "관제 대상"으로 프레이밍하는 효과는 있으나, 강한 클로징 비트가
  없어져 영상이 흐지부지 끝나는 단점 → 채택하지 않음.

## 5. 4번 비트(관제) 구현 범위 — 실기능 vs 연출

관제 화면에서 "태블릿에 알림 뜨고 급하게 대응해서 정지시키는" 장면을 넣고 싶다는 요청이
있었으나, 코드 확인 결과:

- **알림/푸시 시스템**: 없음. `alert` 검색 결과는 전부 "백엔드 연결 끊김" 에러 배너용
  CSS 클래스일 뿐, 이벤트 기반 알림 기능이 아님.
- **태블릿/반응형 UI**: 프론트엔드에 tablet/responsive/mobile 관련 코드 전혀 없음.
- **실제 정지(E-Stop)**: `mission_manager/mission_fsm.py`에 `E_STOP` 상태 값만 정의돼
  있고, 실제 로봇/시뮬레이션을 멈추는 핸들러 연결 여부 미확인 (`exception_scenario.md`도
  "시나리오만 정의, 구현 여부 별도 확인 필요"로 명시).
- **실제로 존재하는 것**: 소터 영역 단위 START/STOP 제어(`WheelSorterController.set_region_enabled`)는
  실제로 동작함.

**결정**: 실제 알림/전면 정지 기능을 새로 구현하지 않음 (D-1 시점 리스크 회피).
- 관제 화면 모니터링 + 실제로 존재하는 제어 버튼 조작은 **실기능으로 촬영**.
- 태블릿에 알림이 뜨는 장면은 **영상 편집(합성)으로만 연출** — 실제 시스템이 멈추지 않아도 됨.

> **갱신**: 어떤 제어 버튼을 쓸지가 이후 논의로 구체화됨 — 소터 영역 STOP/START가 아니라
> **컨베이어 STOP/START + AMR 수동조작(Jog)** 두 가지로 확정. 최종 서사와 구체적 컷 구성은
> 9장 참고.

## 6. 평가 지표 (참고 — 프로젝트 전체 평가 기준표)

영상 자체의 평가 기준은 아니고, 프로젝트 전체(시연 포함)에 대한 평가 배점표. 영상에서
어떤 부분을 강조할지 우선순위 판단에 참고. 이미지로 전달받은 표를 그대로 옮김
(2026-08-27, 원본 이미지 대조 확인 완료).

## 8. 촬영 준비 관련 확인사항 (2026-08-27 코드 조사)

- **랜덤 시드 미고정 (조치 필요)**: `isaac_sim/main_mission.py`는 박스 ID(`random.sample`)와
  목적지(`random.choice`)를 정하는데 `random.seed()`가 코드 어디에도 고정돼 있지 않음.
  분할 촬영을 여러 번 실행해서 진행할 경우, 실행할 때마다 박스 배치/목적지가 달라져
  테이크 간 일관성이 깨질 수 있음 → **촬영 전 `random.seed(고정값)` 추가 필요** (아직 미적용,
  TODO).
- **중간 정지 후 재개(체크포인트) 기능 없음**: `world.reset()`은 시작 시 1회만 호출되고,
  특정 시점 상태를 저장했다가 이어서 재현하는 기능이 없음 → 분할 촬영은 매번 처음부터
  재실행하는 방식이 됨 (시드 고정이 되어 있어야 재실행마다 결과가 일관됨).
- **카메라 위치를 코드로 스폰/이동시키는 기능 없음**: P3020 카메라는 USD에 이미 고정된
  프림 transform을 그대로 읽기만 하고, AMR의 `camera_mount`는 빈 오버라이드, 뷰포트
  카메라를 코드로 옮기는 API 호출도 없음 → 카메라 앵글은 Isaac Sim GUI에서 사람이 직접
  잡고, 화면 녹화 툴로 캡처하는 방식이 현재 코드 구조와 맞음.

| 5 | 물류센터 와이드샷: 우선 처리 완료, 정상 흐름 복귀 | 실물 촬영 |

**핵심 장치 — "3중 매칭"으로 실시간성 증명**: ①알림 문구의 구역명 = ②대시보드에 뜨는
구역명 = ③물류센터 실물 화면 속 그 구역, 이 세 곳을 같은 이름/위치로 매치컷하면 "지금 이
순간의 실제 상황을 보고 있다"는 인과관계가 설명 없이 시각적으로 증명됨.

**검증된 색상 로직** (`frontend/src/components/StatusPill.jsx`, 2026-08-27 코드 확인):
```
positive(초록) = RUNNING, SUCCESS, ONLINE, COMPLETE, UP
negative(빨강) = FAILED, ERROR, OFFLINE, STOPPED
pending(노랑)  = PENDING, WAITING, READY, PAUSED, DOWN
```
→ 컨베이어 STOP을 누르면 상태가 STOPPED가 되어 **빨강**으로 바뀜 (초록 아님). 최초 안이던
"정지 버튼 눌러서 빨강→초록"은 이 로직과 정반대라 반려됨. 확정 서사는 **이미 STOPPED(빨강)
상태를 촬영 전에 미리 만들어두고, START를 눌러 RUNNING(초록)으로 복구하는 것**으로
수정 — 사전 설정만으로 실현 가능, 새 개발 불필요.

**의도적으로 피한 프레이밍**: "시스템이 고장 나서 사람이 고쳤다"가 아니라 "자동화 위에서
필요할 때 사람이 우선순위를 조정하는 하이브리드 제어"로 프레이밍 — 로봇 제어 시스템의
안정성을 깎지 않으면서 관제의 실효성을 보여줌.

`main_mission.py`(Isaac Sim)와 관제 스택(`compose.yaml` + `scripts/run_control_tower_adapters.sh`)을
평소처럼 같이 띄운 뒤, **녹화 시작 전에** 아래 순서로 웹 대시보드에서 직접 조작해 "문제
상황"을 미리 만들어둔다. 이후 정상 시나리오(2번 비트 등)와는 초기 상태가 반대라 세션 A와
분리해서 이 세션에서만 진행한다.

4. 두 상태(컨베이어 STOPPED, AMR 이탈)가 확인되면 카메라를 잡고 **여기서부터 녹화 시작**

참고: 대시보드 상단 "CREATE MISSION" 폼에 이미 region 선택지 `A/B/C/UNKNOWN`이 있어서,
알림 문구의 "B구역"을 이 기존 옵션과 맞추면 3중 매칭(9장 상단)에 자연스럽게 활용 가능.

## 10. 태블릿 화면 렌더링 — 실기능 촬영과 목업의 분리

- 프론트엔드는 `body { min-width: 1180px; }`로 고정돼 있고 반응형 미디어쿼리가 전혀 없음
  (`frontend/src/styles.css` 확인). 폰 폭(375~430px)은 물론 태블릿 세로(~810px)도 이 최소
  폭보다 좁아서, **실물 태블릿에 라이브로 그 화면을 띄우면 레이아웃이 깨짐**.
- 단, 9장의 태블릿 장면은 **라이브 렌더링이 아니라 합성**으로 처리하기로 했으므로 이 제약은
  실제 촬영에 영향 없음: 실제 조작(AMR jog, 컨베이어 STOP/START)은 **정상 해상도의
  노트북/모니터 브라우저에서 진짜로 클릭**해 녹화하고, 그 화면 녹화본을 편집 단계에서
  태블릿 목업 프레임에 얹는 방식.
- 이 방식의 장점: 실기능 신뢰성(진짜 클릭 → 진짜 반응)은 그대로 유지하면서, 태블릿
  기기 자체의 해상도 제약에서 자유로움. 목업 합성 시 브라우저 주소창이 함께 보이도록
  캡처 프레임을 잡아야 "웹 기반"이라는 시각적 증거가 유지됨.
